## Candidate and completeness

The test-only candidate is a **scoped exact cosine scan of vector blobs**, not KNN:

1. Evaluate the synthetic model/dimension/deletion/folder predicates against Saves.
2. Inside a read transaction, left-join every eligible ID to the relevant vec table.
   Compare its blob byte-for-byte with `vec_f32(authoritative_json)`.
3. If any eligible row is missing or differs, explicitly return the existing
   exact JSON SQL result and report fallback.
4. Otherwise evaluate `vec_distance_cosine(blob, query_blob)` over every eligible
   row and take the same internal K=200.

This avoids changing the metric and does not assume completeness or freshness.
It also adds an expensive verification scan. Missing and stale-row fallback
checks passed for all 12 completed benchmark cases, outside timed regions.
Only the declared synthetic scopes were prototyped: the candidate is not a
production implementation of all Library filters, lexical/dense fusion, or errors.

The existing vec table cannot simply be trusted: backfill is incremental, stale
rows can remain, table replacement on dimension change discards prior entries,
and the schema has no model partition. Comparing models/dimensions only after
global top-K cannot recover candidates that were already omitted. Matching row
counts alone would not establish freshness or metric compatibility.

block main while executing. At N=10k, roughly 300ms broad adapter p95 is material;

## Options and requested decision

1. **Recommended: retain exact JSON scan; reject this candidate.** Authorize
   finishing the no-change decision, running repository gates, and adjusting the
   benchmark protocol so the current path and candidate have independent bounds.
   Keep N=50k explicitly blocked until measured; do not merely raise its timeout.
2. Design a separately approved strategy for provable index freshness/model/
   dimension tracking and cosine-compatible ranking. That may require persistent
   schema/format changes and is outside the current scope.
3. Separately investigate moving retrieval SQL off main. This can improve
   responsiveness without necessarily reducing computation; worker ownership
   changes need their own design and approval.

Proposed future candidate acceptance threshold (**not approved**):
exact result parity across scopes, model/dimension changes, missing/stale rows
and tie cases; >=25% p95 reduction against exact SQL at N=10k and N=50k for both
broad and 1%/10% scopes in two independent complete runs; fallback cost and
frequency explicitly reported; no production schema or metric change without a
separate approval. Current candidate fails the timing threshold on completed data.

Decision approval: **granted by the user on 2026-10-30** (“yes I aprove”),
in response to the recommendation to retain exact retrieval, reject the prototype,
separate benchmark bounds, and finish repository gates. No production strategy
